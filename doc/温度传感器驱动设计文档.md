# tmp105 温度传感器内核驱动设计文档

> **快速回忆（4 步）**：
>
> ① 设备侧：QEMU 挂 `tmp105`（I2C 从机，地址 **0x48**）+ 设备树加 `ti,tmp105` 节点（挂到 `i2c@9060000`）
>
> ② 驱动侧：**I2C 客户端驱动 + hwmon** → `/sys/class/hwmon/hwmonX/temp1_input`（单位 **m°C**）
>
> ③ 读数：读寄存器 **0x00** 两字节（8.8 定点，12 位有效）→ `m°C = (int16_t)raw * 1000 / 256`
>
> ④ 对照验证：内核自带 `drivers/hwmon/lm75.c` **也支持 tmp105**（但 4.9 版没有 `of_device_id`，只能 `new_device` 手动实例化）→ 用它交叉验证读数

---

## 1. 目标与范围

### 1.1 目标

在 `linux-kmods` 工程里开发**第 1 个内核模块**：一个 **I2C 温度传感器（TI TMP105 / LM75 兼容）内核驱动**，跑在 QEMU 模拟的 `tmp105` 器件上，做到：

1. 设备树自动匹配（`compatible = "ti,tmp105"`）→ 内核自动 probe，不靠手动 `new_device`；
2. 通过 **hwmon 子系统**导出标准 sysfs 接口（`temp1_input` / `temp1_max` / `temp1_min` / `temp1_max_alarm`）；
3. 读数与 QEMU 里可动态修改的 `temperature` 属性一致（动态验证，而不是只读一个固定值）；
4. 与**内核自带 lm75 驱动**做交叉对照，证明"我们的驱动 + 链路"都是对的。

### 1.2 明确不做（第一版）

- 不做用户态 `i2c-dev` 路径（那是 libobject 已有的 [`I2c_TempSensor`](../../libobject/src/board/hal/i2c/I2c_TempSensor.c) 的活）；
- 不做 ALERT 中断的一整套（QEMU 模型有 ALERT，留作 M4 可选）；
- 不做 thermal zone 联动（第二版可选，见 §4.3）；
- 不做多实例/热插拔的完整支持（骨架按单实例写，注明多实例改造点）。

## 2. 现状调研（已确认）

| 项 | 结论 | 依据 |
|---|---|---|
| QEMU 器件模型 | **`hw/sensor/tmp105.c`**（TI TMP105，8.8 定点，寄存器 TEMPERATURE/CONFIG/T_LOW/T_HIGH） | 你的 QEMU 源码 |
| QEMU 可调属性 | **`temperature`**（int，单位 **0.001 °C**，即 m°C）→ 可用 QMP `qom-set` 动态改 | `tmp105_initfn()` 里 `object_property_add(... "temperature" ...)` |

| 当前 dtb 挂载 | **只挂了 `eeprom@50`（atmel,24c02）**，**没有 tmp105 节点** → 需要补 | 同上 |
| 内核既有支持 | `drivers/hwmon/lm75.c` 支持 `tmp105`（`i2c_device_id` 有 `{ "tmp105", tmp105 }`） | 4.9.263 源码 |
| 该驱动的短板 | 4.9 的 lm75.c **没有 `of_device_id`** → 不能靠设备树自动匹配；且当前 **`# CONFIG_SENSORS_LM75 is not set`** | 源码 + `.config` |
| 内核配置前置 | `CONFIG_I2C=y` ✓、`CONFIG_I2C_CHARDEV=y` ✓、**`CONFIG_I2C_DESIGNWARE_PLATFORM=y` ✓**、`CONFIG_HWMON=y` ✓、`CONFIG_OF=y` ✓、`CONFIG_DEBUG_FS=y` ✓ | `.config` |

| libobject 侧对照 | 用户态 [`I2c_TempSensor`](../../libobject/src/board/hal/i2c/I2c_TempSensor.c) 走 `/dev/i2c-N` + `I2C_RDWR`，默认参数就是 **tmp105 / 0x48 / 总线 0** | `doc/board/i2c用户态驱动设计.md` §10 |

> **一句话结论**：QEMU 侧和内核侧都"半成品就绪"——`I2C_DESIGNWARE_PLATFORM` 已使能，**缺的只有两件事**：① QEMU/dtbd 里把 tmp105 挂上；② 一个能按设备树自动 probe 的驱动（4.9 自带的 lm75 正好做不到）。

## 3. 器件规约：TMP105（LM75 兼容）

### 3.1 寄存器（指针寄存器 + 数据，标准 I2C 读写）

| 指针 | 名称 | 宽度 | 说明 |
|---|---|---|---|
| `0x00` | TEMPERATURE | 16 位（读） | 温度，**8.8 定点**、12 位有效、高字节在前 |
| `0x01` | CONFIG | 8 位 | 关断/模式/极性/故障队列/分辨率/**单次转换** |
| `0x02` | T_LOW | 16 位 | 下限阈值（9 位有效 → 0.5 °C 步进） |
| `0x03` | T_HIGH | 16 位 | 上限阈值（同上） |

### 3.2 数据格式与换算（关键，务必背下来）

- 寄存器里是 **8.8 定点**（1 LSB = 1/256 °C = 3.90625 m°C），**有符号**（负温度按二进制补码，例如 −0.0625 °C = `0xFFF0`）；
- 12 位模式下低 4 位恒为 0（即实际步进 1/16 °C = 0.0625 °C），阈值只有 9 位有效（步进 0.5 °C）；
- **统一换算公式**（对温度和阈值都成立，不用区分器件模式）：

```c
/* raw 是 0x00 读回来的两个字节按大端拼成的 int16 */
int32_t temp_mC = (int32_t)(int16_t)raw * 1000 / 256;   /* 结果单位 m°C，hwmon 要求 */
```

- hwmon sysfs 的 `temp1_input` **单位必须是 m°C**（不是 1/1000 之外的任何变体）；负温度直接是负值，例如 `temp1_input = -6250` 表示 −6.25 °C。

### 3.3 CONFIG 寄存器（第一版只读不写，第二版用）

| 位 | 名称 | 第一版处理 |
|---|---|---|
| 0 | SHUTDOWN | 不碰（保持器件默认） |
| 1 | TM（Comparator / Interrupt） | 不碰；M4 若做 ALERT 再动 |
| 2 | POL（ALERT 极性） | 不碰 |
| 3:4 | F（故障队列） | 不碰 |
| 5:6 | R0/R1（分辨率） | 不碰（QEMU 固定 12 位语义）；**读数公式对分辨率不敏感，无需改** |
| 7 | ONE-SHOT（单次转换） | 不碰；若要"按需唤醒省电"再用 |

> **注意**：R0/R1、ONE-SHOT 的位定义在 TMP105 与 LM75 上**语义不同**（LM75 的 R0/R1 是分辨率/比较模式），所以驱动若将来要写 CONFIG，必须按 `compatible` 分支处理 —— 这也是"别硬编码某一型号"的原因（libobject 的 `I2c_TempSensor` 文档里同样强调这一点）。

### 3.4 报警机制（QEMU 已实现，M4 可选）

QEMU 的 tmp105 实现了 comparator / interrupt 两种模式：温度 ≥ `T_HIGH` 触发 ALERT、< `T_LOW` 解除/触发（取决于 TM 位）。第一版只把 `T_LOW/T_HIGH` 暴露成 hwmon 的 `temp1_min/temp1_max`，**不注册中断**；`temp1_max_alarm` 通过"重读温度与阈值比较"实现（软件比较，简单可靠）。

## 4. 内核侧架构选择

### 4.1 选定：I2C 客户端驱动 + hwmon（with_info）

```
用户态                       内核
cat /sys/class/hwmon/hwmon0/temp1_input
        │
        ▼
   hwmon 核心 ────────── tmp105_hwmon.ko（本模块）
        │                     │  i2c_smbus_read_word_swapped() 读 0x00
        ▼                     ▼
                    ┌──────────────────┐
                    │ i2c 核心 (i2c-0) │  ← snps,designware-i2c 控制器驱动
                    └──────────────────┘
                              │ I2C 总线（SCL/SDA，开漏+上拉）
                              ▼
                    QEMU tmp105 从机 @0x48
```

**理由**：

1. **这是内核里温度传感器的标准归宿**：温度传感器 → hwmon（`temp1_*`）；不用自定义字符设备/ioctl，用户态零适配；
2. **单位与命名是稳定 ABI**：`temp1_input`(m°C) 是约定，`name` 为 `tmp105`，用户态按 `name` 找设备（不依赖 `hwmonN` 序号）；
3. 4.9 已提供 `devm_hwmon_device_register_with_info()`（`is_visible/read/write` 三回调），代码比 `_with_groups` 短且是主推风格；
4. **能按设备树匹配**（`of_device_id` + `i2c_device_id` 双表），正好补上 4.9 自带 lm75 的短板。

### 4.2 备选（不选，仅记录）

| 方案 | 何时才用 |
|---|---|
| 自定义字符设备 + ioctl | 有**非 hwmon 语义**的控制面（大量私有 ioctl、DMA 缓冲）时的骨架参考；本模块不做 |
| `sysfs` 手写属性组（`_with_groups`） | 想支持极老内核（<4.5）时；本项目不做 |
| 直接 `i2c-dev` 用户态 | libobject 已经做了（[`I2c_TempSensor`](../../libobject/src/board/hal/i2c/I2c_TempSensor.c)），内核态重做无意义 |

### 4.3 第二版可选：thermal zone 联动

若要做"过温关机/降频"这类**策略**，不应写在传感器驱动里，而应把它注册成 **thermal zone**（`thermal_zone_device_register`，`CONFIG_THERMAL=y` 已开）或用 `thermal` 的 hwmon 桥接。第一版只做 hwmon，保持职责单一。

## 5. 驱动设计（tmp105_hwmon）

### 5.1 源文件与模块名

- 目录：`drivers/tmp105_hwmon/`，文件 `tmp105_hwmon.c`，Kbuild：`obj-m := tmp105_hwmon.o`
- **模块名故意不叫 `tmp105.ko`**：避免与将来打开 `CONFIG_SENSORS_LM75=m` 时的概念混淆（那个驱动内部 handle 也叫 tmp105）；hwmon 的 `name` 仍用 `"tmp105"`（对外语义清晰）。
- 许可：**`MODULE_LICENSE("GPL")`**（内核模块用 GPL 符号的合规要求，见 §10.2）。

### 5.2 关键数据结构

```c
struct tmp105_data {
	struct device		*hwmon_dev;
	struct i2c_client	*client;
	struct mutex		lock;		/* 保护寄存器访问与缓存 */
	int			resolution;	/* 1/16 °C = 1（占位：为将来支持 9~11 位） */
};

/* 常量 */
#define TMP105_REG_TEMP		0x00
#define TMP105_REG_CONF		0x01
#define TMP105_REG_T_LOW	0x02
#define TMP105_REG_T_HIGH	0x03
#define TMP105_TEMP_SCALE_DIV	256		/* 8.8 定点 */
```

### 5.3 probe / remove 流程（全部 `devm_*`，免手动回收）

```c
static int tmp105_probe(struct i2c_client *client, const struct i2c_device_id *id)
{
	struct tmp105_data *data;

	/* 不检查 I2C_FUNC_SMBUS_WORD_DATA：现在几乎所有适配器都有；
	 * 若目标平台没有，用 i2c_smbus_read_byte_data 拼也不难 —— 见 §5.4 备注 */
	data = devm_kzalloc(&client->dev, sizeof(*data), GFP_KERNEL);
	if (!data)
		return -ENOMEM;

	data->client = client;
	mutex_init(&data->lock);

	/* 关键：注册 hwmon，把"温度通道"声明出来（channels 表见 §5.5） */
	data->hwmon_dev = devm_hwmon_device_register_with_info(&client->dev,
				"tmp105", data, &tmp105_chip_info, NULL);
	if (IS_ERR(data->hwmon_dev))
		return PTR_ERR(data->hwmon_dev);

	i2c_set_clientdata(client, data);
	dev_info(&client->dev, "tmp105 at 0x%02x (adapter %s)\n",
		 client->addr, client->adapter->name);
	return 0;
}
/* remove 不需要做事：devm_* 自动注销 */
```

### 5.4 读温度 / 读写阈值（唯一碰寄存器的地方）

```c
static int tmp105_read_temp_mC(struct tmp105_data *data, int *mC)
{
	s32 raw;

	mutex_lock(&data->lock);
	raw = i2c_smbus_read_word_swapped(data->client, TMP105_REG_TEMP);
	mutex_unlock(&data->lock);
	if (raw < 0)
		return raw;				/* 传播 -EREMOTEIO/-ENXIO 等 */

	*mC = (int32_t)(int16_t)raw * 1000 / TMP105_TEMP_SCALE_DIV;
	return 0;
}
```

> **为什么用 `read_word_swapped`**：TMP105 是"高字节在前"的 16 位寄存器，而 SMBus `read_word` 是**低字节在前**；`swapped` 版本正好把它换回来，省掉手工拼字节。这也是 mainline lm75.c 的做法。
>
> **没有 `SMBUS_WORD` 支持时**：退化为两次 `i2c_smbus_read_byte_data(reg)` / `(reg+1)` 手动拼 `(hi << 8) | lo`，语义完全一致。
>
> 阈值读写同理（`T_LOW/T_HIGH`），写的时候要**按 0.5 °C 量化**（`raw = (mC / 500) << 7`），避免写进去被器件截断成"看起来不一样的值"。

### 5.5 hwmon 接口声明（with_info 风格）

```c
static const struct hwmon_channel_info *tmp105_channel_info[] = {
	HWMON_CHANNEL_INFO(chip, HWMON_C_REGISTER_TZ),	/* 可选：声明支持注册时区 */
	HWMON_CHANNEL_INFO(temp,
			HWMON_T_INPUT | HWMON_T_MAX | HWMON_T_MIN | HWMON_T_MAX_ALARM,
			HWMON_T_INPUT | HWMON_T_MAX | HWMON_T_MIN | HWMON_T_MAX_ALARM, /* 第二路留着 */
			HWMON_T_INPUT /* 终止项 */),
	NULL
};
```
> 注：`HWMON_CHANNEL_INFO` 宏与 `hwmon_channel_info` 的具体写法以 4.9 的 `include/linux/hwmon.h` 为准（写代码时对照 `drivers/hwmon/*.c` 的现成例子，比如 `drivers/hwmon/tmp102.c`）。**设计阶段只约定"暴露哪 4 个属性"**：
> `temp1_input`（m°C）、`temp1_max`、`temp1_min`、`temp1_max_alarm`。

`read` 回调实现三件事：
1. `temp1_input` → `tmp105_read_temp_mC()`；
2. `temp1_max/min` → 读 `T_HIGH/T_LOW`；
3. `temp1_max_alarm` → 读温度与 `T_HIGH` 比较（**软件比较**，不依赖 ALERT 引脚）。

### 5.6 设备匹配（两套表，缺一不可）

```c
static const struct i2c_device_id tmp105_id[] = {
	{ "tmp105", 0 },
	{ }
};
MODULE_DEVICE_TABLE(i2c, tmp105_id);

static const struct of_device_id tmp105_of_match[] = {
	{ .compatible = "ti,tmp105" },
	{ .compatible = "national,lm75" },	/* LM75 兼容器件可复用 */
	{ }
};
MODULE_DEVICE_TABLE(of, tmp105_of_match);

static struct i2c_driver tmp105_driver = {
	.driver = {
		.name	= "tmp105_hwmon",
		.of_match_table = tmp105_of_match,
	},
	.probe		= tmp105_probe,
	.id_table	= tmp105_id,
};
module_i2c_driver(tmp105_driver);
```

> `module_i2c_driver()` 一次性搞定 init/exit，比手写 `module_init/module_exit` 更不容易漏。

### 5.7 并发 / 错误 / 边界

| 关注点 | 做法 |
|---|---|
| 并发 | 所有寄存器访问走 `mutex_lock(&data->lock)`；hwmon 的 read 是进程上下文，可睡 |
| I2C 失败 | `i2c_smbus_*` 返回负值 → 直接向上传播，hwmon 层会返回给用户态（`-EREMOTEIO` 常见于 NACK） |
| 负温度 | 用 `(int16_t)` 强转保证符号扩展；测试必须覆盖（见 §9.4） |
| 越界值 | 不做钳位（器件量程 −55~125 °C 外的值本身就说明链路有问题，宁可在测试里 assert） |
| 设备不存在 | 设备树/`new_device` 配错时 probe 不会触发 → 用 `i2cdetect` 先确认 0x48 有响应 |

## 6. 与标准的对齐（为什么这样导出）

| 约定 | 值 | 原因 |
|---|---|---|
| 子系统 | hwmon | 温度传感器在内核里的标准归宿 |
| 单位 | **m°C**（`temp1_input`） | hwmon ABI 规定；不要用 1/100 °C 或浮点 |
| `name` | `tmp105` | 用户态用 `/sys/class/hwmon/*/name` 定位，避免依赖 `hwmonN` 序号 |
| 属性名 | `temp1_input/max/min/max_alarm` | hwmon 标准命名，`sensors` 命令可直接读 |
| 匹配方式 | `of_device_id` + `i2c_device_id` | 前者支持设备树自动 probe，后者支持 `new_device`/模块参数兼容 |
| 对外 ABI | 只在 sysfs；**不加私有 ioctl** | 一旦加了就变成"必须维护的稳定 ABI" |

## 7. 设备侧配置（QEMU + 设备树 + 内核前置）

### 7.1 设备树：给 i2c 控制器加一个从机

在 [`virt_custom.dts`](../../qemu_virt_machine/virt_custom.dts) 的 `i2c@9060000` 节点里追加（**与 eeprom@50 并存，地址不冲突**）：

```dts
	i2c@9060000 {
		compatible = "snps,designware-i2c";
		/* ... 原有属性不变 ... */

		eeprom@50 {
			compatible = "atmel,24c02";
			reg = <0x50>;
		};

		tmp105@48 {                      /* ← 新增 */
			compatible = "ti,tmp105";
			reg = <0x48>;
		};
	};
```

> 重新生成 dtb：`dtc -I dts -O dtb -o virt_custom.dtb virt_custom.dts`，用 `-dtb virt_custom.dtb` 启动。

### 7.2 QEMU：把 tmp105 挂到同一条 i2c 总线上

```sh
qemu-system-aarch64 -M virt -cpu cortex-a72 -nographic \
    -kernel Image -dtb virt_custom.dtb -append "console=ttyAMA0 root=..." \
    -device tmp105,bus=<i2c总线id>          # ← 关键：bus 必须与 dts 的 i2c@9060000 对应
```

- **bus id 怎么确定**：启动时加 `-monitor stdio`，`info qtree` 找 `snps,designware-i2c` 那条总线的 `id`（virt 机器上通常是 `i2c-bus.0`/`i2c-bus.1` 或带路径）；也可先在 dts 里看控制器顺序。
- **不挂上会怎样**：驱动照旧 probe（设备树说了有器件），但每次读温度都 NACK → `-EREMOTEIO`。所以"`i2cdetect` 能看到 0x48"是**第一道验收**。

### 7.3 内核配置前置（当前 `.config` 已满足，除 lm75 对照可选）

| 配置 | 当前 | 作用 |
|---|---|---|
| `CONFIG_I2C=y` | ✓ | i2c 核心 |
| `CONFIG_I2C_DESIGNWARE_PLATFORM=y` | ✓ | **i2c-0 控制器驱动**（没有它 `/dev/i2c-0` 和 probe 都无从谈起） |
| `CONFIG_HWMON=y` | ✓ | hwmon 核心 |
| `CONFIG_OF=y` | ✓ | 设备树匹配 |
| `CONFIG_I2C_CHARDEV=y` | ✓ | `i2cdetect/i2cget` 调试通道 |
| `CONFIG_SENSORS_LM75=m` | **✗（未开）** | **仅用于对照测试**（§9.3）；开了之后也能证明"同一器件两份驱动读数一致" |

## 8. 构建 / 部署 / 调试

### 8.1 构建（外部模块，交叉编译）

```sh
# 本工程默认指向 workspace 里已配置好的 arm64 4.9.263 内核树
make                                   # 等价于下面这条
make -C /home/alan/workspace/linux-4.9.263 M=$PWD/drivers/tmp105_hwmon \
     ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- modules
# 产物：drivers/tmp105_hwmon/tmp105_hwmon.ko
```

> 该内核树里已有 `.config` 与 `Module.symvers` → **外部模块可直接编**；若换新树，先 `make ARCH=arm64 CROSS_COMPILE=... modules_prepare`。

### 8.2 部署（QEMU 里两种方式）

```sh
# 方式 1：rootfs 里放模块 + 启动脚本（推荐，可持久化）
cp tmp105_hwmon.ko <rootfs>/lib/modules/$(uname -r)/extra/
modprobe tmp105_hwmon            # 或 insmod /lib/modules/.../tmp105_hwmon.ko

# 方式 2：用 virtfs/9p 把宿主机目录挂进来（改一次编一次，最方便）
```

## 9. 测试与验收方案（4 层，逐层加码）

### 9.1 L1：链路层（不涉及我们的驱动）

- `i2cdetect -y 0` 看到 `0x48`；
- `i2cget -y 0 0x48 0x00 w` 返回可解释的值（例如 `0x1900` → 25.0 °C）。

**验收**：能稳定读 10 次不报错。

### 9.2 L2：驱动 probe 与 sysfs

- `insmod tmp105_hwmon.ko` → `dmesg` 出现我们的 `tmp105 at 0x48`；
- `/sys/class/hwmon/hwmonN/name == tmp105`，`temp1_input` 在 −55000~125000 之间。

### 9.3 L3：对照与动态（**核心验收**）

1. **与内核自带驱动对照**（需 `CONFIG_SENSORS_LM75=m` + 先卸载我们的驱动）：
   ```sh
   echo tmp105 0x48 > /sys/bus/i2c/devices/i2c-0/new_device   # 4.9 的 lm75 无 of_match，只能这样实例化
   cat /sys/class/hwmon/hwmon*/temp1_input
   ```
   两者在同一温度下**读数应完全一致**（同器件同公式）。
2. **动态改温度**（证明不是读死值）：QMP 里
   ```
   (qemu) qom-set /machine/soc/i2c@9060000/tmp105@48 temperature 30000   # 单位 m°C
   ```
   → `temp1_input` 应随之变化（路径用 `info qom-tree` 确认）。

### 9.4 L4：边界与异常

| 用例 | 期望 |
|---|---|
| 温度为负（如 `-6250` m°C） | `temp1_input` 输出负值，与 `qom-get temperature` 一致 |
| `T_HIGH` 以下/以上 | `temp1_max_alarm` 正确翻转（0/1） |
| 读写 `temp1_max/min` | 写 50000（50 °C）→ 再读回 50000（验证 0.5 °C 量化） |
| 把 dtb 里的 `reg` 改成 `0x49`（器件仍在 0x48） | probe 成功但读温度报 `-EREMOTEIO`（**错误传播**符合预期），不是 oops |
| 反复 insmod/rmmod 100 次 | 无内存泄漏（`slabtop`/`kmemleak` 抽查），`/sys/class/hwmon` 无残留 |

## 11. 风险 / 待确认 / 里程碑

### 11.1 待确认（开工前 1 小时内可验证）

> **这 4 条已在 2026-09-18 全部有答案 —— 见 §12.1「与设计阶段的差异」。**

1. **QEMU 侧 tmp105 的 bus id**：`info qtree` 确认 `-device tmp105,bus=?` 的正确写法（不同 QEMU 版本 virt 的 i2c bus 命名不同）；
2. **你们自研 machine（[`qemu_virt_machine`](../../qemu_virt_machine)）是否已内置 tmp105**：若已内置，就跳过 §7.2，只改 dtb；
3. `hwmon` 的 `HWMON_CHANNEL_INFO` 在 4.9 的具体宏形态（写代码时以 `drivers/hwmon/tmp102.c` 为模板）；
4. 是否需要 `CONFIG_SENSORS_LM75=m` 做对照（需要重新编一次内核模块，几分钟）。

### 11.2 风险

| 风险 | 影响 | 对策 |

| dtb 与 QEMU 器件不一致 | probe 成功但读失败（NACK） | 先跑 L1（`i2cdetect`），再上驱动 |
| 温度换算公式写错（符号/定点） | 读数差 16 倍或负温度乱码 | 单测覆盖 −0.0625 / 0 / 25.0 / 125.0 四个点 |

| 与 lm75 驱动同时绑定同一器件 | 两个驱动抢设备 | 只装一个；对照测试时先 `rmmod` / `echo 0x48 > delete_device` |

## 12. 实测结论（M0~M4，2026-09-18）

全部结论都在 `/home/alan/workspace/qemu/build/qemu-system-aarch64`（v11.1.0-rc2，含自研 virt 改动）
+ `linux-4.9.263`（arm64）上实测得到，可用 `./scripts/verify_qemu.sh` 一键复现（**13 项断言全 PASS**）。

### 12.1 与设计阶段的差异（重要）

| 项 | 设计文档原说法 | 实测 | 影响 |
|---|---|---|---|
| 设备侧配置 | §7.1/§7.2 要改 dts + QEMU 加 `-device tmp105` | **自研 QEMU 已内置**：[`create_i2c()`](../../qemu/hw/arm/virt.c:1622) 里 `i2c_slave_create_simple(bus, TYPE_TMP105, 0x48)`，并自动往 FDT 加 `/i2c@9060000/tmp105@48`（`ti,tmp105`） | **不用改 dtb、不用 `-device tmp105`**。启动时**别传 `-dtb virt_custom.dtb`**（那份 dts 里没有 tmp105 节点，probe 不会触发）。§11.1 的"bus id 待确认"作废。 |
| hwmon API | §5.5 用 `HWMON_CHANNEL_INFO(...)` | 4.9 的 `include/linux/hwmon.h` **没有这个宏**（只有 `struct hwmon_channel_info`） | 必须手写 `tmp105_temp_config[]` + `struct hwmon_channel_info`，风格同树内 `tmp102.c`/`lm75.c`。代码已按此实现。 |
| 温度分辨率 | §3.2 说"12 位有效"，且换算对分辨率不敏感 | QEMU/器件上电默认 **CONFIG=0 → R1:R0=00 → 9 位有效（0.5 °C 步进）** | 换算公式仍通用，但读数落在 0.5 °C 网格上：`qom-set -6250` → `temp1_input = -6500`。第一版不写 CONFIG 是刻意的（§3.3）。 |
| L1 验收 | §9.1 说"`i2cdetect -y 0` 看到 0x48" | **看不到**：busybox `i2cdetect` 报 `can't use SMBus quick write command, will skip some addresses`，只列出 0x50(eeprom) | L1 改用 `i2cget -y 0 48 0x00 w`（实测 `0x0019` = 25.0 °C）。 |
| 对照验收 | §9.3 用 lm75 驱动交叉验证 | `CONFIG_SENSORS_LM75` 仍未开 | 本驱动已能独立完成 L1~L4 验收；lm75 对照降级为**可选**（要重编一次内核模块）。 |

### 12.2 新发现的坑（已写进[开发规范](开发规范.md) §8）

1. **驱动绑定后 `i2c-dev` 会 EBUSY**：`i2cget -y 0 0x48 ...` 报
   `can't set address to 0x48: Device or resource busy` → L1 的原始寄存器对照必须放在 `insmod` 之前。
2. **开机自带一条 I2C WARN（与本驱动无关）**：0.9 s 时
   `WARNING: CPU: 0 PID: 1 at drivers/i2c/busses/i2c-designware-core.c:293 i2c_dw_clk_rate+0x3c/0x44`
   （DesignWare I2C 在 virt 上取不到输入时钟的 `WARN_ON_ONCE`）。
3. **QEMU stdout 是块缓冲**：串口日志"何时可读"不可控，`sleep`+`grep` 会随机失败 →
   取值类断言改为"客户机写 9p 共享目录，宿主轮询文件"。
4. **`info qom-tree` 打印的是相对对象名**（如 `/device[10]`），不是完整 QOM 路径；实测完整路径是
   `/machine/unattached/device[10]`，[`qmp_set_temp.py`](../scripts/qmp_set_temp.py) 用 `qom-list` 遍历自动定位。

### 12.3 实测数据（`./scripts/verify_qemu.sh`）

|---|---|---|
| L1 | `i2cget -y 0 48 0x00 w` | `0x0019`（= 25.0 °C，与 QEMU 初始 `temperature=25000` 一致） |
