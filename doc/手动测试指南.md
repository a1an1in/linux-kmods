# tmp105_hwmon 手动测试指南（只用驱动接口）

> **验证入口只有一个：我们驱动导出的 hwmon 接口**
> `/sys/class/hwmon/hwmonN/{name,temp1_input,temp1_max,temp1_min,temp1_max_alarm}`。
> 本文不使用 `i2cget`/`i2cset` 等第三方命令做交叉验证（它们的定位见[设计文档 §4.4](温度传感器驱动设计文档.md)）。
> 全篇只给手动命令，不需要跑脚本；带 ✅实测 的输出都是在这套环境里跑出来的原样结果。
>
> 唯一"不经过驱动"的操作是**宿主侧改 QEMU 的环境温度**（`qom-set`）—— 那是"制造测试条件"，
> 不是验证手段；验证仍然只看 `temp1_input`。
>
> 想一次性跑完的自动化版本在 [`scripts/verify_qemu.sh`](../scripts/verify_qemu.sh)（那个脚本另外用 `i2cget`
> 做了一次独立交叉验证，属自动化脚本的选择，本指南不使用）。手动测试不需要跑任何脚本。

**三条前提**（不知道会白折腾）：

1. **启动不要加 `-dtb`**：自研 QEMU 会自动生成含 `/i2c@9060000/tmp105@48`（`compatible = "ti,tmp105"`）的 FDT；
   而 `virt_custom.dtb` 那份 dts 里**没有** tmp105 节点，加了 `-dtb` 驱动就不会 probe。
2. **"环境温度"只能宿主侧改**：器件寄存器 `0x00` 是只读的（真实 TMP105 亦然，QEMU 对写 0x00 直接忽略），
   所以客户机里改不了测量温度 —— 这是"环境量"，由宿主用 QMP 扮演（见 §4）。
3. **单位是 m°C，且器件默认 9 位（0.5 °C 步进）**：`temp1_input=25000` 就是 25.0 °C；
   `-6.25 °C` 这类值会被器件量化到 `-6.5 °C`（`-6500`），属正常。

## 3. 驱动接口验证（全部在客户机 shell 里，只读写 hwmon sysfs）

### 3.1 加载驱动，确认设备树自动 probe

```sh
mkdir -p /mnt
mount -t 9p -o trans=virtio,version=9p2000.L kmods /mnt
insmod /mnt/drivers/tmp105_hwmon/tmp105_hwmon.ko
dmesg | tail -3
```
✅实测：`tmp105_hwmon 0-0048: tmp105 at 0x48 on Synopsys DesignWare I2C adapter`
（`0-0048` 就是 i2c-0 上的 0x48；说明 `compatible = "ti,tmp105"` 匹配成功，probe 走的是设备树路径。）

### 3.2 定位设备 + 出厂默认值

```sh
for d in /sys/class/hwmon/hwmon*; do
    [ "$(cat $d/name)" = tmp105 ] && echo "找到：$d"
done
```
✅实测：`找到：/sys/class/hwmon/hwmon0`（**按 `name` 定位，不依赖 hwmonN 序号**）

```sh
T=/sys/class/hwmon/hwmon0
for f in name temp1_input temp1_max temp1_min temp1_max_alarm; do
    echo "$f=$(cat $T/$f)"
done
```
✅实测：

| 接口 | 值 | 含义 |
|---|---|---|
| `name` | `tmp105` | 用户态定位用的稳定标识 |
| `temp1_input` | `25000` | 25.0 °C（单位 m°C，QEMU 上电初值） |
| `temp1_max` | `80000` | 80.0 °C（器件上电默认 T_HIGH） |
| `temp1_min` | `75000` | 75.0 °C（器件上电默认 T_LOW） |
| `temp1_max_alarm` | `0` | 软件比较结果：25 < 80 → 0 |

### 3.3 阈值读写：0.5 °C 四舍五入 + 量程钳位

```sh
T=/sys/class/hwmon/hwmon0

echo 50000   > $T/temp1_max; cat $T/temp1_max     # 可精确表示
echo 12345   > $T/temp1_max; cat $T/temp1_max     # 不是 0.5 的整数倍 → 四舍五入
echo 300     > $T/temp1_max; cat $T/temp1_max
echo -300    > $T/temp1_max; cat $T/temp1_max
echo -100000 > $T/temp1_max; cat $T/temp1_max     # 低于量程 → 钳位
echo 200000  > $T/temp1_max; cat $T/temp1_max     # 高于量程 → 钳位
echo -55000  > $T/temp1_min; cat $T/temp1_min     # 下限可精确表示
echo 80000   > $T/temp1_max; echo 75000 > $T/temp1_min   # 恢复出厂默认
```

✅实测结果：

| 写入 | 读回 | 规则 |
|---|---|---|
| `50000` | `50000` | 可精确表示，原样保留 |
| `12345` | `12500` | 按 **0.5 °C 四舍五入**（12.345 → 12.5） |
| `300` | `500` | 0.3 → 0.5 |
| `-300` | `-500` | −0.3 → −0.5（四舍五入，不是截断） |
| `-1` | `0` | 极小值 → 0 |
| `-100000` | `-55000` | 低于量程 → **钳位到 −55 °C** |
| `200000` | `125000` | 高于量程 → **钳位到 125 °C** |
| `125000` / `-55000` | `125000` / `-55000` | 量程端点可精确表示 |

写入被驱动量化后落到器件的 8.8 定点寄存器，所以读回来是"量化后的值"，这是设计行为（不是丢数据）。

### 3.4 报警翻转（纯驱动接口）

`temp1_max_alarm` 是驱动做的**软件比较** `temp1_input >= temp1_max`（不依赖 ALERT 引脚）：

```sh
T=/sys/class/hwmon/hwmon0
echo T=$(cat $T/temp1_input)                     # 先看当前温度
echo 20000 > $T/temp1_max; cat $T/temp1_max_alarm   # 阈值 20 < 当前 25 → 1
echo 90000 > $T/temp1_max; cat $T/temp1_max_alarm   # 阈值 90 > 当前 25 → 0
echo 80000 > $T/temp1_max                           # 恢复默认
```
✅实测：`T=25000`、`1`、`0`。

### 3.5 环境温度变化 → `temp1_input` 跟随（宿主侧发条件，客户机看接口）

改温度的命令见 §4（⌃A c 或 `nc -U`）。改完后在串口里只读我们的接口：

```sh
cat /sys/class/hwmon/hwmon0/temp1_input
```

✅实测对照：

| 宿主 `qom-set temperature` | 客户机 `cat temp1_input` | 说明 |
|---|---|---|
| `30000` | `30000` | 动态跟随，证明读的不是死值 |
| `-6000` | `-6000` | 负温度、符号扩展正确（可精确表示） |
| `-6250` | `-6500` | 器件默认 9 位（0.5 °C）量化到 −6.5 °C，正常 |

### 3.6 反向用例：地址不对 → probe 成功、读接口报错

造一个"器件不存在"的实例（这一步不改设备树，只是让驱动再 probe 一个错误地址）：

```sh
insmod /mnt/drivers/tmp105_hwmon/tmp105_hwmon.ko                # 0x48 正常起来（hwmon0）
echo tmp105 0x49 > /sys/bus/i2c/devices/i2c-0/new_device
dmesg | tail -2

for d in /sys/class/hwmon/hwmon*; do
    echo "$d:$(cat $d/name):$(cat $d/temp1_input 2>&1)"
done

echo 0x49 > /sys/bus/i2c/devices/i2c-0/delete_device             # 撤销
```
✅实测：
- `tmp105_hwmon 0-0049: tmp105 at 0x49 on Synopsys DesignWare I2C adapter`（probe 成功）
- `hwmon0:tmp105:25000`
- `hwmon1:tmp105:cat: read error: Remote I/O error` ← 即 `-EREMOTEIO`（从机 NACK），**不是 oops**
- `delete_device` 后 `hwmon1` 干净消失

结论：错误按设计向上传播到用户态接口，符合"probe 不该因器件缺失而失败"的约定。

### 3.7 反复加载/卸载（接口与资源残留检查）

```sh
rmmod tmp105_hwmon
ls /sys/class/hwmon                      # 应无 hwmon0 残留

    rmmod tmp105_hwmon; insmod /mnt/drivers/tmp105_hwmon/tmp105_hwmon.ko

```

## 4. 制造"环境温度变化"（宿主侧，唯一非驱动操作）

**为什么必须宿主侧**：测量温度是 QEMU 器件的 `temperature` 属性（"环境"），
TMP105 的 `0x00` 寄存器只读（真实器件也如此），客户机里任何写都改不了它。
详情：QEMU 的写入路径 [`tmp105_write()`](../../qemu/hw/sensor/tmp105.c:158) 里
`case TMP105_REG_TEMPERATURE:` 是空的；而宿主侧 setter 是
[`tmp105_set_temperature()`](../../qemu/hw/sensor/tmp105.c:102)（直接改模型内部状态，不经过 I2C 总线）。

### 4.1 方式 1：`Ctrl-A c` 切到 monitor（方式 1 启动时）

```
Ctrl-A c                                     # 切到 QEMU monitor（再按一次切回串口）
(qemu) info qom-tree                         # 找类型为 (tmp105) 的那一行
(qemu) qom-get /machine/unattached/device[10] temperature
(qemu) qom-set /machine/unattached/device[10] temperature -6000
(qemu) qom-set /machine/unattached/device[10] temperature 30000
```

### 4.2 方式 2：monitor socket + `nc -U`（方式 2 启动时，不按键）

在**另一个宿主终端**里：

```sh
printf 'info qom-tree\n' | nc -U /tmp/tmp105-mon.sock | grep tmp105
#   ✅实测：    /device[10] (tmp105)          ← HMP 打印的是相对对象名，完整路径要自己拼

printf 'qom-get /machine/unattached/device[10] temperature\n' | nc -U /tmp/tmp105-mon.sock
printf 'qom-set /machine/unattached/device[10] temperature -6000\n' | nc -U /tmp/tmp105-mon.sock
#   ✅实测：设完回串口 cat temp1_input → -6000
```
> 非 tty 场景下 HMP 会把输入回显成一堆 `ESC[K` 转义，看着乱但不影响结果；在真终端里手敲就干净了。
> 超范围会被 QEMU 拒绝：`qom-set ... 128000` → `value 128.000 C is out of range`。

### 4.3 `Ctrl-A c` 按不出来时

- QEMU 侧本身没问题：✅实测在方式 1 的参数下，往串口灌字节 `0x01 0x63`（= ⌃A c）能切进 `(qemu)` 并切回。
- 多半是终端把 ⌃A 拦了（VS Code 集成终端、部分 GUI 终端）；换 `xterm`/`gnome-terminal`，
  或直接用 §4.2 的 monitor socket（根本不按键）。
- 输入不是 tty（被重定向/管道）时 mux 也收不到按键。

## 5. 接口一览与预期

| 接口 | 单位/取值 | 权限 | 读/写 | 实测（出厂状态） |
|---|---|---|---|---|
| `name` | 字符串 | `0444` | 只读 | `tmp105` |
| `temp1_input` | m°C | `0444` | 只读 | `25000` |
| `temp1_max` | m°C（0.5 °C 量化，钳位 −55~125 °C） | `0644` | 读写 | `80000` |
| `temp1_min` | 同上 | `0644` | 读写 | `75000` |
| `temp1_max_alarm` | 0/1（软件比较 `input >= max`） | `0444` | 只读 | `0` |

## 6. 现象速查（驱动/接口视角）

| 现象 | 原因 | 处理 |
|---|---|---|
| `insmod` 成功但 `/sys/class/hwmon` 里没有 tmp105 | 设备树没匹配（最常见：加了 `-dtb virt_custom.dtb`） | 不加 `-dtb`；`dmesg | grep i2c` 看是否有 0-0048 |
| `cat temp1_input` 报 `Remote I/O error` | 该实例的地址上没有器件（如 §3.6 的 0x49） | 检查 `reg`/`new_device` 地址；真实器件在 0x48 |
| 读数是 `-6500` 而不是 `-6250` | 器件默认 9 位（0.5 °C）分辨率 | 正常，见 §3.5 |
| 写 `temp1_max` 再读回来不一样 | 阈值按 0.5 °C 四舍五入 + 量程钳位 | 正常，见 §3.3 实测表 |
| `temp1_max_alarm` 一直是 0 | 阈值比当前温度高（比较条件是 `input >= max`） | 把阈值压到低于当前温度，见 §3.4 |
| `echo` 写 `temp1_max` 报 `Permission denied` | 该文件是 `0644`，需要 root（客户机里默认就是 root） | 用 root 写；只读场景用 `0444` 的 `temp1_input` |
| 开机出现 `WARNING ... i2c_dw_clk_rate` | DesignWare I2C 在 virt 上取不到输入时钟，**与本驱动无关**（0.9 s 时、早于本模块） | 忽略 |
| `rmmod` 提示 `Module tmp105_hwmon is not currently loaded` | 没加载（或已卸载） | 正常，先 `insmod` |
